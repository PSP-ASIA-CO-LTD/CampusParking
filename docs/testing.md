# กระบวนการทดสอบและโค้ดที่ใช้ทดสอบ

เอกสารนี้ตอบโจทย์ข้อ 1 ของงานรอบล่าสุด คืออธิบายว่าโปรเจกต์นี้ทดสอบอย่างไร ใช้อะไรทดสอบ ตัดสินใจเลือกเคสจากอะไร และมีอะไรที่ทดสอบอัตโนมัติไม่ได้บ้าง

---

## 1. ภาพรวม ทดสอบสองชั้น

| ชั้น | จำนวน | ใช้ตอนไหน | ใครรัน |
|---|---|---|---|
| **เทสอัตโนมัติ** | 73 เคส | ทุกครั้งที่แก้โค้ด ใช้เวลาไม่ถึง 1 วินาที | `dart test` |
| **ทดสอบด้วยมือ** | 48 เคส | ก่อนส่งงาน และหลังเปลี่ยนกฎ | พิมพ์ input เองทีละเคส |

**ทำไมต้องมีทั้งสองชั้น**

เทสอัตโนมัติเร็วและรันซ้ำได้ไม่จำกัด แต่มันมองไม่เห็นสิ่งที่อยู่บนหน้าจอจริง เช่นคำถามเรียงถูกลำดับหรือไม่ ข้อความที่แสดงอ่านรู้เรื่องไหม ส่วนการทดสอบด้วยมือเห็นทุกอย่างที่ผู้ใช้เห็น แต่ช้าและทำซ้ำทุกครั้งที่แก้โค้ดไม่ไหว

จึงแบ่งหน้าที่กัน คือ **ตรรกะการคิดเงินและกฎทะเบียนให้เทสอัตโนมัติดูแล ส่วนลำดับการถามและหน้าตาของหน้าจอให้คนดูแล**

## 2. เครื่องมือที่ใช้

ใช้ `package:test` ซึ่งเป็นแพ็กเกจทดสอบทางการของทีม Dart ประกาศไว้ใน `pubspec.yaml` ใต้ `dev_dependencies` คู่กับ `package:lints` ที่เป็นชุดกฎให้ analyzer ทั้งสองตัวติดตั้งเฉพาะตอนพัฒนา ไม่ติดไปกับโปรแกรมที่ส่งมอบ

```bash
dart pub get                                   # ติดตั้ง dependency
dart test                                      # รันทั้งหมด
dart test test/plate_rules_test.dart           # รันเฉพาะไฟล์เดียว
dart test --name "motorcycle"                  # รันเฉพาะเคสที่ชื่อมีคำนี้
```

ไม่ได้ใช้สคริปต์ช่วยรันใด ๆ ทุกคำสั่งข้างบนเป็นคำสั่งมาตรฐานของ Dart เอง

นอกจากนี้ยังใช้เครื่องมือตรวจคุณภาพอีกสองตัวควบคู่กัน

```bash
dart format --output=none --set-exit-if-changed .   # ตรวจว่าจัดรูปแบบครบ
dart analyze                                        # ตรวจ error และ warning
```

## 3. โครงสร้างไฟล์เทส

```text
test/
├── parking_fee_calculator_test.dart   33 เคส   กฎการคิดเงิน
├── parking_summary_test.dart           5 เคส   การสะสมยอดประจำวัน
└── plate_rules_test.dart              35 เคส   กฎที่อ่านจากทะเบียนรถ
```

**แบ่งไฟล์ตามสิ่งที่ทดสอบ ไม่ใช่ตามประเภทของเทส** ไฟล์เทสหนึ่งไฟล์คู่กับไฟล์โค้ดหนึ่งไฟล์ เวลาเทสแดงจะได้รู้ทันทีว่าต้องไปเปิดไฟล์ไหน

| ไฟล์ | ทดสอบอะไร | ตัวอย่างเคส |
|---|---|---|
| `parking_fee_calculator_test.dart` | ค่าจอดตามเวลา เพดานราคา ส่วนลดสมาชิก บัตรหาย | จอด 15 นาทีต้องฟรี, จอด 500 นาทีต้องติดเพดาน |
| `parking_summary_test.dart` | ตัวนับและยอดรวมสะสมถูกต้องเมื่อทำหลายรายการ | ทำ 3 รายการแล้วยอดรวมต้องเป็น 44 |
| `plate_rules_test.dart` | ทะเบียนแบบไหนเข้ากฎ แบบไหนไม่เข้า | `12-ABC` เป็นสมาชิก, `12-` ไม่เป็น |

## 4. รูปแบบการเขียนเทสที่ใช้

### 4.1 Arrange, Act, Assert

ทุกเคสแบ่งเป็นสามช่วงชัดเจน เตรียมข้อมูล เรียกใช้งาน แล้วตรวจผล (คอมเมนต์ Arrange / Act / Assert ด้านล่างเพิ่มเข้ามาเพื่ออธิบายในเอกสารนี้ ในไฟล์เทสจริงใช้บรรทัดว่างคั่นแทน)

```dart
test('Car parked for 15 minutes should be free', () {
  // Arrange เตรียมของที่ต้องใช้
  final calculator = ParkingFeeCalculator();
  final transaction = ParkingTransaction(
    plate: 'ABC123',
    vehicleType: 'car',
    duration: 15,
    isMember: false,
    lostTicket: false,
  );

  // Act เรียกสิ่งที่ต้องการทดสอบ เพียงครั้งเดียว
  final result = calculator.calculateFee(transaction);

  // Assert ตรวจว่าผลตรงกับที่คาดไว้
  expect(result.normalFee, 0);
  expect(result.finalFee, 0);
});
```

การแบ่งสามช่วงทำให้เวลากลับมาอ่านทีหลัง รู้ทันทีว่าบรรทัดไหนคือ input บรรทัดไหนคือสิ่งที่ทดสอบ และบรรทัดไหนคือคำตอบที่คาดหวัง

### 4.2 ตั้งชื่อเคสเป็นประโยคที่อ่านรู้เรื่องโดยไม่ต้องเปิดโค้ด

ใช้รูป `<สิ่งที่ทดสอบ> should <ผลที่คาดหวัง>` เสมอ

```text
Car parked for 15 minutes should be free
A plate with nothing after the hyphen should not be a member
No plate can be both a car plate and a motorcycle plate
```

เหตุผลคือเวลาเทสแดง Dart จะพิมพ์ชื่อเคสออกมา ถ้าชื่อดีพอ จะรู้ว่าพังเรื่องอะไรตั้งแต่ยังไม่เปิดไฟล์

### 4.3 เขียนตัวเลขให้เห็นกับตาในเคส ไม่ซ่อนไว้ในตัวแปรร่วม

ทุกเคสสร้าง `ParkingFeeCalculator` และ `ParkingTransaction` ของตัวเองใหม่ทุกครั้ง ถึงจะดูซ้ำซ้อนแต่แลกมาด้วยสองอย่าง

- **อ่านเคสเดียวจบ** ไม่ต้องเลื่อนขึ้นไปดูว่าตัวแปรร่วมถูกตั้งค่าอะไรไว้
- **เคสไม่กวนกันเอง** ถ้าเคสหนึ่งเผลอแก้ค่าในวัตถุร่วม เคสอื่นจะพังตามโดยไม่มีเหตุผล ซึ่งเป็นบั๊กของเทสที่หายากที่สุดแบบหนึ่ง

### 4.4 ใส่ `reason` ในเคสที่ผลลัพธ์ไม่บอกอะไรด้วยตัวเอง

```dart
test('No plate can be both a car plate and a motorcycle plate', () {
  List<String> plates = [
    'AB1234',
    'AB123',
    'ab1234',
    '12-ABC',
    '12-ABCD',
    'ABC',
    'ABC123',
  ];

  for (String plate in plates) {
    expect(
      isCarPlate(plate) && isMotorcyclePlate(plate),
      isFalse,
      reason: 'ทะเบียน $plate เข้าทั้งสองกฎ ซึ่งไม่ควรเกิดขึ้น',
    );
  }
});
```

เคสนี้วนหลายทะเบียน ถ้าไม่มี `reason` เวลาแดงจะเห็นแค่ `Expected: false Actual: true` ซึ่งไม่บอกว่าทะเบียนไหนเป็นตัวปัญหา

## 5. เลือกเคสมาจากอะไร

ไม่ได้เขียนเทสเพื่อให้ตัวเลข coverage สวย แต่เลือกจากจุดที่โค้ดมีโอกาสผิดจริง 4 แบบ

### 5.1 ขอบของเงื่อนไข

ทุกที่ที่มีการเปรียบเทียบ จะทดสอบทั้งฝั่งก่อนขอบ ตรงขอบ และหลังขอบ

| เงื่อนไขในโค้ด | เคสที่เขียน |
|---|---|
| `duration > 15` | 15 นาที (ฟรี) และ 16 นาที (เริ่มคิดเงิน) |
| ปัดชั่วโมงขึ้น | 60 นาที (1 ชม.) และ 61 นาที (2 ชม.) |
| เพดานราคา | 500 นาที ที่คำนวณได้เกินเพดาน |
| `input.length < 3` | ทะเบียน 2 ตัว และทะเบียน 3 ตัวพอดี |

### 5.2 กฎสองข้อทำงานพร้อมกัน

เช่นสมาชิกที่บัตรหาย หรือทะเบียนที่เข้าทั้งกฎสมาชิกและกฎมอเตอร์ไซค์ กรณีพวกนี้เป็นจุดที่ลำดับของกฎมีผลต่อผลลัพธ์

### 5.3 ข้อตกลงระหว่างกฎที่ต้องไม่เปลี่ยน

บางเคสไม่ได้ทดสอบตรรกะใหม่เลย แต่เขียนไว้เพื่อ **จดข้อตกลงลงในโค้ด** ว่าสิ่งนี้ต้องเป็นจริงเสมอ

```dart
test('A plate can be both a member plate and a motorcycle plate', () {
  expect(isMemberPlate('12-ABC'), isTrue);
  expect(isMotorcyclePlate('12-ABC'), isTrue);
});
```

ถ้าวันหน้ามีคนแก้กฎข้อใดข้อหนึ่งจนไปกระทบอีกข้อ เทสตัวนี้จะแดงขึ้นมาเตือนทันที

### 5.4 กรณีที่ยอมรับแล้วเสียประโยชน์

เช่นทะเบียน `12-` ที่ตอนแรกผ่านกฎสมาชิก แปลว่าใครพิมพ์ `12-` เข้ามาก็ได้ส่วนลดฟรี กรณีแบบนี้เมื่อเจอแล้วจะเพิ่มเคสลงไปทันทีเพื่อไม่ให้หลุดอีก

## 6. อะไรที่ทดสอบอัตโนมัติไม่ได้ และทำไม

มีสองจุดในโปรเจกต์นี้

**จุดที่หนึ่ง การรับ input ผูกอยู่กับ `stdin`**

```dart
int? readDuration() {
  while (true) {
    stdout.write('Parking duration (min) (type "$cancelCommand" to cancel): ');
    String? line = stdin.readLineSync();   // <- ตรงนี้ทำให้เทสไม่ได้
    ...
  }
}
```

เทสเรียกฟังก์ชันนี้ไม่ได้ เพราะมันจะหยุดรอให้คนพิมพ์ เคสอย่าง `abc`, `-1`, ค่าว่าง จึงต้องทดสอบด้วยมือเท่านั้น

**จุดที่สอง `printReceipt()` คืนค่าเป็น `void`**

มันพิมพ์ออกหน้าจอเลยโดยไม่คืนข้อความกลับมา เทสจึงไม่มีอะไรให้ตรวจ ถ้าอยากเทสได้ต้องแยกเป็น `buildReceipt()` ที่คืน `String` แล้วให้ `printReceipt()` เรียกใช้อีกที

**บทเรียนที่ได้จากสองจุดนี้** คือความสามารถในการทดสอบเป็นเรื่องของ **การออกแบบ** ไม่ใช่เรื่องของความขยัน ตอนทำกฎทะเบียนจึงจงใจแยก `lib/plate_rules.dart` ออกมาเป็นฟังก์ชันล้วนที่ไม่ยุ่งกับหน้าจอตั้งแต่แรก ผลคือเขียนเทสครอบได้ครบ 35 เคสโดยไม่ต้องรันโปรแกรมจริงเลย

## 7. การทดสอบด้วยมือ 48 เคส

ตารางเต็มอยู่ในหัวข้อ Test Matrix ของ `README.md` แบ่งเป็น 6 กลุ่มตามที่โจทย์กำหนด บวกกลุ่มกฎทะเบียนที่เพิ่มมาภายหลัง

**วิธีรันทีละเคส**

```bash
printf '1\nABC123\ncar\n16\nn\n3\n' | dart run bin/main.dart
```

**กติกาที่ถือเคร่งครัด**

- ช่อง Actual จะถูกกรอกก็ต่อเมื่อ **ได้รันจริงและเห็นผลบนหน้าจอแล้วเท่านั้น** ไม่กรอกจากการคำนวณในหัวหรือการคาดเดา
- ถ้ากฎเปลี่ยน ช่อง Actual ของเคสที่เกี่ยวข้องจะถูกล้างทิ้งทันที เพราะผลเดิมวัดมาจากกฎเก่า ใช้ยืนยันกฎใหม่ไม่ได้
- ปัจจุบันตารางทั้ง 48 เคสอยู่ในสถานะ **รอรันใหม่ทั้งหมด** เพราะกฎทะเบียนทำให้ลำดับคำถามเปลี่ยนไป

## 8. เทสจับบั๊กอะไรได้จริงบ้าง

ส่วนนี้บันทึกไว้ตามจริง ทั้งกรณีที่เทสช่วยได้และกรณีที่ช่วยไม่ได้

| บั๊กที่เจอ | ใครจับได้ |
|---|---|
| ทะเบียน `12-` ผ่านกฎสมาชิก ทำให้ได้ส่วนลดฟรี | การรีวิวโค้ดด้วยตา แล้วจึงเพิ่มเทสล็อกไว้ |
| โปรแกรมวนถามไม่รู้จบเมื่อ input หมดกลางคัน | การทดสอบด้วยมือ |
| ค่าปรับบัตรหายยังถูกคิดอยู่หลังกฎเปลี่ยน | เทสอัตโนมัติแดงทันทีที่แก้กฎ |
| `else` หายไปใน `bin/main.dart` ทำให้กฎประเภทรถถูกเขียนทับ | **ไม่มีเทสตัวไหนจับได้** เจอจากการรันโปรแกรมจริงแล้วสังเกตว่ายังถามประเภทรถอยู่ |

บรรทัดสุดท้ายสำคัญที่สุด บั๊กนั้นอยู่ใน `bin/main.dart` ซึ่งเป็นส่วนที่เทสอัตโนมัติเข้าไม่ถึง และเป็นบั๊กที่ **คอมไพเลอร์ก็จับไม่ได้** เพราะวงเล็บปีกกาลอย ๆ เป็นไวยากรณ์ที่ถูกต้องใน Dart

ข้อนี้ยืนยันว่าเทสอัตโนมัติ 73 เคสไม่ได้แปลว่าโปรแกรมไม่มีบั๊ก มันแปลว่า **ส่วนที่ทดสอบไว้ยังทำงานถูกอยู่** เท่านั้น การรันโปรแกรมจริงด้วยมือจึงยังจำเป็น

## 9. สิ่งที่จะปรับในรอบถัดไป

**แยกส่วนตรวจสอบออกจากส่วนอ่าน input** เพื่อให้เคสที่ตอนนี้ทดสอบด้วยมือได้อย่างเดียว กลายเป็นเทสอัตโนมัติ

```dart
// lib/input_rules.dart  ตรวจอย่างเดียว ไม่แตะ stdin จึงเทสได้
int? parseDuration(String input) {
  int? value = int.tryParse(input.trim());
  if (value == null || value < 0) {
    return null;
  }
  return value;
}
```

`bin/main.dart` จะเหลือแค่วนถามและพิมพ์ข้อความ ส่วนตรรกะการตัดสินว่ารับหรือไม่รับย้ายไปอยู่ใน `lib/` ที่เทสได้ แนวคิดเดียวกับที่ใช้กับ `plate_rules.dart` แล้วได้ผลดี

ยังไม่ทำในรอบนี้เพราะอยู่นอกขอบเขตที่ได้รับมอบหมาย และการเปลี่ยนโครงของส่วนรับ input จะกระทบตารางทดสอบด้วยมือทั้งตารางอีกรอบ
